# Синхронизация GUtv Event и проверка кода

Проверены общие возможности актуального `gutv_booker`: UI `cc95e03`, backend `b695a07`. В event перенесены профиль, фото с кадрированием и смена робота, независимые устройства, отзыв сессий и выход на всех устройствах, общий интерфейс списков и серверная пагинация с поиском, статусами и историей заявок пользователя. Специфичные для оборудования галереи, корзина и распределение экземпляров не относятся к заявкам на мероприятия. Telegram отсутствует по требованию пользователя.

## Данные представителя

При регистрации обязательны ФИО, организация и контакты. В профиле можно изменить их для будущих заявок. Сервер игнорирует переданные в заявке данные представителя и подставляет профиль. Каждая заявка хранит отдельный снимок: последующее изменение профиля не переписывает её историю.

Миграция `20261004120000_profiles_sessions` восстанавливает данные старых аккаунтов из последней заявки с валидным JSON. Если данных нет, пользователь заполняет профиль один раз. Старые заявки и хеши паролей сохраняются. Старые JWT без идентификатора устройства и прежние refresh-токены перестают действовать — после обновления требуется повторный вход.

## Исправления безопасности и ошибок

- Один refresh-токен на аккаунт заменён таблицей устройств. На сервере хранятся только SHA-256 хеши случайных refresh-токенов; обновление токена атомарно и одноразово.
- JWT проверяется вместе с живой сессией и состоянием пользователя в БД. Заблокированный пользователь не может читать данные с ранее выданным токеном. Блокировка отзывает сессии; снятие блокировки их не восстанавливает. Роль берётся из БД.
- Выход отзывает серверную сессию; можно отозвать только собственные устройства. Отозванный access-токен перестаёт работать сразу.
- Устранено зависание параллельных клиентских запросов при ошибке refresh. Общий Promise возвращает ошибку всем ожидающим запросам. Web Locks координируют обновления в нескольких вкладках; старый ответ не перезаписывает новый вход.
- Быстрый SHA-256 для паролей заменён асинхронным scrypt. Старые пароли обновляются после успешного входа; сравнение выполняется через timingSafeEqual. [Документация Node.js](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).
- Добавлены сохраняемые в SQLite лимиты входа и регистрации, ограничения типов и размеров JSON, полей, фото и идентификаторов. Непроверенные заголовки IP не используются для обхода лимитов.
- Фото ограничены 5 МБ и 20 млн пикселей. Сервер проверяет реальный формат JPG/PNG/WebP и перекодирует изображение в WebP 512×512, удаляя исходные метаданные. SVG и произвольные внешние URL не принимаются.
- Решения администратора выполняются в транзакции с повторной проверкой роли, блокировки, сессии и состояния заявки. Конкурирующие решения не могут воскресить отменённую заявку.
- Списки ограничены выбранной областью доступа. Размер страницы не превышает 100. Поиск учитывает регистр кириллицы и работает по всей выборке; для старых записей поисковый текст заполняется партиями по 100.
- Ошибки Prisma не выдаются клиенту. Исправлена проверка статуса, некорректных ID и административных комментариев. Добавлены nosniff, запрет iframe и ограничения Permissions-Policy.
- Обновлены уязвимые зависимости, включая Next.js. Зафиксированы overrides для исправленных `mysql2` и `deepmerge-ts`, используемых Prisma. Команды генерации клиента, миграций и сборки проверены с ними.
- Vercel Analytics подключается только в окружении Vercel: локальный запуск не запрашивает отсутствующий analytics endpoint.

## Проверки

- `npm test`: правила мероприятий, параллельное обновление токенов, ошибки refresh, защита от устаревшего ответа, миграция старых профилей и повреждённого JSON.
- `npm run test:integration`: production-сборка и HTTP API на отдельной временной SQLite-базе. Проверяются четыре типа заявок, права, сроки, снимки профиля, два устройства, ротация/отзыв, блокировка, старые пароли, фото, лимиты, пагинация, поиск кириллицы и конкурирующая модерация.
- `npm run lint`, `npx tsc --noEmit`, `npm audit`: проверка кода, типов и зависимостей.
- В браузере визуально проверены профиль на ширине 1280 и 390 пикселей, мобильный редактор аватара и форма заявки с данными из профиля. Проверка API сохранения профиля и загрузки фото выполнена интеграционными тестами.

Проверка относится к исходному коду и локальному окружению. Production reverse proxy, TLS, секреты, политики хранения данных и инфраструктура не проверялись. Токены в браузере сохраняются в localStorage, поэтому защита от XSS остаётся важной; переход на HttpOnly cookie потребует отдельного изменения контракта авторизации. Лимиты общего входа и регистрации следует соотнести с реальным трафиком. Удаление аккаунта по существующему API каскадно удаляет его заявки. Отдельного восстановления пароля и MFA в приложении нет.
